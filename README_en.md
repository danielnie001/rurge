### Introduction

rurge (**Ru**st + Su**rge**) is a cross-platform network proxy written in Rust. Its goal is to re-implement, phase by phase, the full feature set of [Surge](https://nssurge.com/) (macOS / iOS) while being:

- **Natively compatible with Surge's configuration format**: `.conf` profiles, `.sgmodule` modules, `RULE-SET` / `DOMAIN-SET` rule sets, `policy-path` subscriptions and managed profiles work as-is (`#!MANAGED-CONFIG` and a remote `#!include` are downloaded into the data directory and refreshed on their `interval` while `rurge run` is running; the differences from Surge are registered in section 1.3 of the [compatibility matrix](docs/surge-compatibility-matrix.md); see Status);
- **Compatible with Surge's scripting API**: existing `http-request` / `http-response` / `cron` / `event` / `dns` / `rule` / `generic` scripts run unchanged;
- **Compatible with Surge's HTTP API**: existing dashboards and automation tools can connect directly;
- **Core first, cross-platform**: one command-line daemon shared by Windows / Linux / macOS, with a desktop GUI planned for a later phase.

### Status

> **Phase 1: milestones M1 through M4b and the two addenda that followed are merged, and the proxy works end to end.** The phase 1 addendum (M5b) did three things that had never been done: a managed profile (`#!MANAGED-CONFIG`) is downloaded into the data directory on its `interval` while `rurge run` is running (rurge never rewrites your file, so what is downloaded is a copy) and is checked before it is taken — a download that does not load, or is not a profile (a captive portal's page, say), is not taken and the previous copy stays in effect —, `strict` makes rurge refuse new sessions when an update that is due has not succeeded (the API stays up), and a taken update reloads the profile; a remote `#!include` is downloaded, cached and refreshed the same way; and external resources can be listed with `GET /v1/external_resources` and updated at once with `POST /v1/external_resources/update`. A user name and password written in a download's URL (`https://user:pass@host/…`) are sent as Basic authentication (the manual does not say whether Surge sends them; over an `http://` URL they travel in clear text; registered in the `RULE-SET` row of section 3.1 of the compatibility matrix). Downloaded text gains no rights by being included: it starts no local program and names no local rule-set, domain-set or `policy-path` file (nor does a managed profile's copy `#!include` any local file), so a local `#!include`, an `external` policy, a local set or a `policy-path` in a managed profile's copy differs from what the manual describes (the manual has no such restriction; not checked on Surge); the differences are registered in sections 1.3 and 10.4 of [docs/surge-compatibility-matrix.md](docs/surge-compatibility-matrix.md). > **Phase 3 (enhanced mode / TUN) has started, and M1 (network environment and subnets), M2 (process identification) and M3 (the TUN core) are done — M3 was done and tested only on an in-memory device, `rurge run` does not start a virtual interface yet, and users will not see it before M4.** The overall design of phase 3 and the detailed designs and implementation plans of M1, M2 and M3 are written (`docs/superpowers/specs/`, `docs/superpowers/plans/`; Chinese). M1 needs no virtual interface; it is the half that already helps the traffic arriving through the system proxy and the proxy ports today: rurge reads the network the machine is on (primary interface, default gateway, interface kind, the Wi-Fi name; each platform has its own reader — Windows and Linux compare every 2 seconds, macOS listens on a routing socket), and when the network changes it flushes the DNS cache, makes `url-test` / `fallback` / `load-balance` groups measure again, and has WireGuard take new carriers; `subnet` policy groups choose their member by the current network (a temporary override can be set with `POST /v1/policy_groups/select` and is cleared when the network changes), and `SUBNET` rules match the current network; `[SSID Setting]` can swap the DNS servers on a given network, or pause the takeover of the system proxy (`suspend=true`; the enhanced-mode half comes with M4). **A behaviour change**: a `subnet` group without `default` is now a load error (it used to fall back as an empty group). The Wi-Fi name cannot be read where Windows has no location permission, in a macOS 14+ daemon and a few other places; `SSID:` / `BSSID:` conditions then never match, without an error, while `TYPE:` and `ROUTER:` work as usual. The Linux and macOS readers were only tested against fake machines on the Windows development machine; their tests were compiled and run on Linux and macOS in CI's run 39022550224 and passed once (one of them reads the machine it runs on and asserts only invariants); the manual checklist [docs/acceptance/phase3-manual.md](docs/acceptance/phase3-manual.md) (Chinese) has not been carried out at all; the differences from Surge are registered in the [compatibility matrix](docs/surge-compatibility-matrix.md) (Chinese; sections 2.3, 3.1, 3.4, 5.1, 5.2, 9.4 and others), and the API and log lines are in [docs/api/phase3.md](docs/api/phase3.md) (Chinese). M2 (process identification) is done as well: `PROCESS-NAME` rules now match the process a session comes from (Windows reads the system's TCP / UDP connection tables and the image path of the process, Linux reads `/proc/net` and finds the process by inode, macOS reads the PCB tables of `sysctl` and `proc_pidpath`; only the system's tables are read, and again no virtual interface is needed — the connections that reach rurge from this machine through the system proxy and the proxy ports already have a process to look up), and the request records and `GET /v1/requests/recent` / `active` carry two new keys, `pid` and `processPath`. When a rule reaches `PROCESS-NAME` and the process has not been found yet, it waits for at most 200 milliseconds and then decides as if the process were unknown (a note on the session says so); connections from other devices on the LAN, from virtual machines, WSL2 or containers have no socket on this machine, and their process is unknown. **A change of reading**: a `PROCESS-NAME` value that starts with a drive letter (`C:\`, `d:/`) or `\\` is now a path (it used to be taken for a file name, which never matched); on Windows file names and paths are compared without regard to case and `.exe` is not dropped (the manual only speaks of the Mac; this is rurge's own reading); the two process lines of the built-in set `SYSTEM`, `trustd` and `netbiosd`, take effect only on macOS. A process's name, path and PID appear only in the DEBUG log, the request records and the API. The Linux and macOS readers were only tested against fixtures on the Windows development machine and are to be checked on the first CI run; the M2 section of the manual checklist has not been carried out at all; the differences from Surge are registered in the [compatibility matrix](docs/surge-compatibility-matrix.md) (Chinese; sections 3.1, 3.5, 9.4 and 10.4), and the API and log lines are in [docs/api/phase3.md](docs/api/phase3.md) (Chinese). M3 (the TUN core) is the half that `rurge run` will need once it starts a virtual interface, done and tested on an **in-memory device**: the new crate `rurge-tun` (one code base for all three platforms) sends the IP packets that come in to a user-space TCP stack (smoltcp, sharded by four-tuple), UDP sessions per source endpoint of the app, ICMP echo and the DNS responder, and TCP connections and UDP datagrams go through the engine's existing pipeline by rules and policies; the fake-IP pool (`198.18.0.0/15` and `fd00:6152::/64`; the mapping between names and addresses is kept in `fake-ip.txt` in the data directory) lets connections to a fake address go to the name behind it. The **DNS responder** (port 53 of `198.18.0.2`, over UDP and TCP, plus the servers `hijack-dns` names) answers A and AAAA with fake addresses (names exempted by `always-real-ip` get real ones), refuses SVCB and HTTPS according to `allow-dns-svcb`, answers NXDOMAIN to Firefox's canary domain, and forwards every other type to the upstreams as `[Host]`'s `server:` says; the `REJECT` family of `pre-matching` rules refuses early at two layers, DNS and SYN (the DNS layer has no connection, so conditions about ports and destination addresses are read as "not known" and a `NOT` cannot turn them into refusing everything; from the 50th refusal of one host within 30 seconds on, the refusal is upgraded to `REJECT-DROP`; one rule appears in the request log once in 5 minutes); sessions that come through the HTTP / SOCKS5 listeners with a fake address as the destination are turned back into the name too. **Not done**: the real devices, addresses, routes, the takeover of the system DNS and loop avoidance (M4) — so `rurge run` does not start a virtual interface today, and no command-line option can; after a plain HTTP request that came through a listener with a fake address has been turned back into the name, its request line and `Host` are still the fake address (the HTTP engine of phase 4 will fix that). Numbers on the development machine (a Windows 11 x86-64 development machine, release build, in-memory device): a single stream does about 5 to 7 Gbit/s in each direction (the gate is 0.7), ten thousand idle connections plus a hundred active ones take about 402 MB on rurge's side (NFR-01's 300 MB, at the 70% of the target that phase 3 is to reach, is a line of 429 MB; the conservative reading is about 15 MB over, and whether to change the budget is for the project owner), and the latency of a fake answer inside the core (the device not included) has a median under 1 microsecond (NFR-01 asks for under 0.2 milliseconds); the numbers on a real device, and what real applications (browsers, `dig`, `nslookup`, resolvers with 0x20 case randomisation) do when they ask the responder, have not been observed. CI has not run the commits of M2 and M3; the M3 section of the manual checklist (19 items, to be done after M4) has not been carried out at all; the differences are registered in the [compatibility matrix](docs/surge-compatibility-matrix.md) (Chinese; sections 4.1, 6.4, 9.1 and others), and the API and log lines are in [docs/api/phase3.md](docs/api/phase3.md) (Chinese). Next comes M4 (platform integration: the virtual interfaces of the three platforms, addresses and routes, the takeover of the system DNS, and loop avoidance).

### Quick start (planned)

> `rurge check`, `rurge rule match`, `rurge dns lookup` and `rurge run` (HTTP / SOCKS5 proxy, DIRECT / REJECT, and the upstreams of every phase-2 outbound protocol (see the feature table above) — the TCP ones optionally wrapped in Shadow TLS — including `underlying-proxy` chains) work today; `select` / `url-test` / `fallback` / `load-balance` / `smart` / `subnet` groups work. The HTTP API and `rurge reload` / `stop` / `status` are available (see [docs/api/phase1.md](docs/api/phase1.md); phase-2 additions in [docs/api/phase2.md](docs/api/phase2.md)). `rurge run --system-proxy` points the system proxy at rurge and restores it on exit, or at the next start after a crash; `rurge service install | uninstall [--user] [--dry-run]` registers or removes automatic startup (systemd / launchd / a Windows scheduled task). On macOS, `networksetup` usually needs an administrator account; whether `sudo` is required has not been verified on real hardware yet (see [docs/acceptance/phase1-manual.md](docs/acceptance/phase1-manual.md)) — on failure, rurge passes the tool's error through as-is. `rurge run` also takes rurge-specific runtime options — `--idle-timeout`, `--request-log-size`, `--watch` (hot reload), `--log-file` (daily rotation), `--empty-group-reject` (a policy group without members rejects instead of going direct), `--listen-http` / `--listen-socks5` (replace the profile's listen addresses) — as CLI flags / env vars only, never written into the Surge profile. When a profile has a `#!MANAGED-CONFIG` line or a remote `#!include` whose content is not in the data directory yet, `rurge run` first waits for the first download (one line on standard error says so; at most 60 seconds; not with `--no-network`); `rurge check`, `rurge rule match`, `rurge dns lookup` and `rurge reload` / `stop` / `status` only read what has already been downloaded and never go online for the profile (`reload` / `stop` / `status` also take `--data-dir`).

```bash
# Build
cargo build --release

# Validate a profile
rurge check -c config.conf

# Test offline which rule a request would hit and which policy it resolves to (no daemon needed)
rurge rule match -c surge.conf www.example.com --explain

# Resolve a name offline through the profile's DNS settings
rurge dns lookup -c surge.conf www.example.com --trace

# Run
rurge run -c config.conf

# Run and point the system proxy at rurge (restored on exit, or at the next start after a crash)
rurge run -c config.conf --system-proxy

# Preview what registering automatic startup would do (drop --dry-run to install)
rurge service install -c config.conf --user --dry-run
```

Profiles use the Surge format directly; see the example under 「配置文件直接采用 Surge 格式」 in [README.md](README.md) (Chinese).
