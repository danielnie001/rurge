# 阶段 1 需求逐句对照代码

## 怎么读

这份文档把 `docs/requirements.md` 第 4 节里所属阶段含阶段 1 的功能需求，一句一句对着手册、代码和用例读过一遍。读的是一个助手：它读代码、读用例的断言、补用例、修小处的缺口；每条结论另由一位评审者抽查，把同样的三样东西重读一遍。2026-10-13 起读，起点是提交 `1f1938a`；读的过程中补的用例与一处修复在其后的提交里，表里逐条写明提交。表里引用的路径、函数和用例名，在写表时的工作区用 `git grep` 逐个核对过。

**一行是需求里的一句话。** 需求在分号、顿号和括号里的枚举处切开，一项一行。手册一页列出几十个键的（`[General]` 的 58 个），按手册自己的分组一组一行，用例是把手册那一页的键逐个写出来断言的一条表驱动用例。

**五列。**

| 列 | 内容 |
| --- | --- |
| 需求 | 需求编号 |
| 这一句 | 用需求自己的话引的那一句，长的用 `…` 缩短 |
| 结论 | 下面六种之一，别的写法都不用 |
| 代码 | 真正**作用于**这件事的地方，`路径::函数`；只有解析器接受它而没有东西用它的，不算"做了" |
| 用例 | 路径与用例名；读过它的断言，断言的是这一句说的行为，不是"跑通了" |

**六种结论。**

- `做了`：代码在，也有一条会因这一句不成立而红的用例。
- `做了，补了用例`：代码在，读的时候没有这样的用例（把代码改坏一行，所有现有用例照样通过）；补了，并且在改坏的代码上看到它红。用例格式后面括号里是补它的提交。
- `补上了`：这一句没做，或只做了一部分，读的时候当场补上；先红后绿，一处一个提交。
- `没有做完（已登记）`：要先有设计才能做，没有做；缺什么、使用者会看到什么写在代码列，登记进收尾的"没有做完的"。
- `有意不同（已登记）`：rurge 有意做成了别的样子，代码列写差异登记在哪（兼容性清单的哪一节或哪份设计），用例列写 rurge 现在做的是什么。
- `不属于阶段 1` 与 `需求文字有问题`：结论后面括号里用一句话说为什么——所属阶段在后面、或需求文字同手册、同另一条需求不符、所属阶段标错。

**这份文档没有覆盖的。** 需要真实桌面环境的手工验收（系统代理三个平台、服务安装），清单在 `docs/acceptance/phase1-manual.md`，没有一行做过；CI 没有绿过，三个平台只在一台 Windows 11 x86-64 的开发机上跑过。表里写"只在 Unix 上编译"的用例、macOS 与 Linux 上的系统信息读取，本机没有编译过或运行过。判为"做了"的行说的是：有一条用例断言了这一句；不是说别处没有缺口。

`FR-CFG-11`（`[Keystore]`，阶段 2）与 `FR-CFG-13`（模块，阶段 5）的所属阶段栏没有阶段 1，不在这一节。
