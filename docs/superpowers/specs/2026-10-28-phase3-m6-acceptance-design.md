## 1. 范围

四件事：

### 3.4 非功能需求

需求文档第 5 节里与阶段 3 直接相关的四条（NFR-01、NFR-11 的文字点了阶段 3；NFR-05 的网络切换恢复靠阶段 3 的 FR-IN-09；NFR-07 点了 `rurge-tun`），只读与阶段 3 相关的那一部分：

- NFR-01：“目标值（阶段 1 与阶段 3 建立基准后校准）”与“fake-IP 应答 < 0.2 ms”——证据是 M3 与 M5 的基准读数（`docs/testing.md` 的基准一段、M5 记录第 61 ～ 63 行），只是内存里的设备；校准没有做（没有真实设备上的数，总设计 Q7）。
- NFR-05：“网络切换后自动恢复（重建 socket、清缓存、重测、重建 WireGuard）”。
- NFR-07：“平台特定代码隔离在 `rurge-platform` 与 `rurge-tun`；CI 在三平台构建与测试”。用一条脚本核对平台 `cfg` 出现在哪里：`cfg(…)`、`cfg!(…)`、`cfg_attr(…)` 里有 `unix`、`windows`、`target_os` 的都算，把 `cfg!` 的值当参数传下去的选择处也算。读评审者的问题时扫过一遍（M6-D20）：除了可执行文件的选择处与只在用例里的，库 crate 的生产代码里还有几处——`rurge-config` 的 `Platform::current`、`rurge-dns` 的 fake-IP 池文件在 Unix 上只给所有者读写、`rurge-rules` 的 `PROCESS-NAME` 在 Windows 上不分大小写与路径归一化、`SYSTEM` 集的两行 `PROCESS-NAME` 只在 macOS 上编进去（M2-D17）。判法：可执行文件的选择处与用例里的不算违背；生产代码里其余的每一处，有设计的已决事项写着的算登记过，没有的列进「没有做完的」、去向项目所有者（挪进平台层，还是改 AR-02 / NFR-07 的字面）。这一句全部登记过的记 `有意不同（已登记）`，有一处没有登记的记 `没有做完（已登记）`。不当场挪代码（要先有设计）。
- NFR-11：“Wintun 等驱动的再分发条款在阶段 3 确认”——证据是调研报告第 7 节与 M4d 的做法（使用者自己放 `wintun.dll`、校验签名）；“确认”没有做到书面确认（总设计 Q3），照实写。

## 4. 怎么读

### 4.1 一句一行

切法照阶段 1（`phase1-acceptance.md`「怎么读」）：需求在分号、顿号和括号里的枚举处切开，一项一行；手册一页列出几十个键的，按手册自己的分组一组一行。“这一句”一格用需求自己的话引，长的用 `…` 缩短。切法在任务 0 定下、协调者审过，之后的任务不再改切法（要改，写一行修正记录）。

### 4.2 六列

| 列 | 内容 |
| --- | --- |
| 需求 | 需求编号；第 3.2 节的两张表写 `第 7 节`，第 3.3 节的表写原来的编号与出处 |
| 这一句 | 同阶段 1 |
| 结论 | 第 4.4 节的八种之一 |
| 代码 | 真正**作用于**这件事的地方，`路径::函数`；只有解析器接受它而没有东西用它的，不算“做了” |
| 用例 | 路径与用例名；读过它的断言，断言的是这一句说的行为，不是“跑通了”；只在某个平台上编译的，写明平台 |
| 真机上 | 第 4.3 节 |

### 4.3 “真机上”一列（M6-D3）

阶段 3 的大多数句子，内存设备上的用例证明了逻辑，真的网卡、路由、系统 DNS 与真实应用的反应要在真机上看——这正是 VCRM 里“演示”与“测试”分开记的理由。这一格写：

- 手工清单的编号（`W19`、`M17`、`L18`、`P29` 一类），一个平台一个或几个；
- L2 特权用例的名字（`tests/` 下环境变量门控的那一份），注明“没有运行过”；
- `—`：L1 的用例已经证明了这一句的全部，不需要真机（例如解析、诊断、纯函数）；
- `看不出`：要真机才证得了，但在真机上也没有一项手工操作看得出它（例如 `udp-priority` 只在高负载时让 UDP 先写，M5 照实没有设手工项）；括号里一句话说为什么（M6-D21）。

要真机而手工清单里没有对应项、又不是“看不出”的，这一格写“缺”，任务 6 补项（第 7 节）。

### 4.4 八种结论（M6-D4）

阶段 1 的七种照用（把“不属于阶段 1”换成“不属于阶段 3”），定义一字不改：`做了`、`做了，补了用例`、`补上了`、`没有做完（已登记）`、`有意不同（已登记）`、`不属于阶段 3`、`需求文字有问题`。另加一种：

- `做了，本机没有能红的用例`：代码在，作用于这一句，但没有一条缺省的用例会因这一句不成立而红，在这台开发机上也补不出来。有两种（M6-D21）：
  - 它只在 Linux 或 macOS 上编译（`cfg(target_os = "linux")`、`cfg(target_os = "macos")`、`cfg(unix)`），本机编译不到；
  - 它在本机编译，但只在有特权、真设备或签名的 DLL 时才运行——直接调操作系统的 FFI（例如 Wintun 的建网卡、收发包）、真的执行系统命令的那一层——缺省的用例照规矩从不走到它。

  代码一格写明那段代码与原因（它的 `cfg`，或“要特权 / 真设备 / DLL”），用例一格写“—”或断言不到这一句的那几条用例，L2 的用例写在「真机上」一格；这些句子另列一节「本机没有能红的用例的」，给以后能在那个平台上、或以特权跑的会话（或所有者）补。

**逻辑钉住了、系统的效果没有钉住的，记 `做了`**（阶段 1 的先例：FR-IN-04 系统代理三个平台的几行）：L1 的用例把作用于这一句的逻辑一直钉到系统的边界——假执行器收到的逐字命令、路由集、恢复的计划——改坏那段逻辑会有用例红，就记 `做了`；系统真的照做没有，是“真机上”一格的事。只有作用于这一句的代码整段都没有缺省用例走到时，才用 `做了，本机没有能红的用例`。

已经有一条只在 Linux / macOS 上编译、会因这一句而红的用例的，记 `做了`，用例一格写“只在 Linux 上编译；CI 运行 40611702392 通过”（那次运行之后加的用例写“CI 没有见过”）。

### 4.5 当场补的尺度（M6-D5）

照阶段 1 / M5b 任务 12：一处代码、一条用例补得上的（M5a 那些小项的尺度），当场补——先写会红的用例、在改坏的（或没有补的）代码上看到它红、再补到绿——，一处一个提交；补上的那一行记 `补上了`，用例一格后面括号里写提交。另加两条限制：

- **只补本机能编译、能运行的代码**。要改的地方只在 Linux 或 macOS 上编译的，不改，登记（这台开发机编译不到它，第一次编译它的是 CI——M5 的派工规矩同样如此）。`rurge-platform` 与 `rurge-tun` 里本机编译、缺省用例也跑得到的代码（例如 Windows 一侧照夹具解析的读法、平台无关的路由集），照同样的尺度可以当场补；**不**当场补的是：加或改 `unsafe` 的函数（`LISTED` 的名单）、FFI 的调用、新的平台后端、在真机上执行的系统命令的内容——它们在本机证不了，登记（M6-D23）。
- **不改已经登记的行为**。一处行为在兼容性清单、API 参考或手工清单里写着的，要改它就是改登记，不是补缺口：登记，不当场改，交给所有者。

要先有设计、要加依赖、要动平台代码、要改登记的，记 `没有做完（已登记）`：代码一格写缺什么、使用者今天看到什么，登记进「没有做完的」，去向写项目所有者。

### 4.6 改坏验证（M6-D6）

`做了` 的句子，读用例的断言读不出它会因这一句而红的，做一次改坏验证：改一行让这一句不成立、跑那条用例、看到它红、改回去。照 `CLAUDE.md`「测试约定」：动手之前先说清这一改会让哪些会话、查找、下载与文件去哪里，可能离开回环或写到用例的临时目录之外的不做；改动与红的输出记进工作区的日志，报告里列出；改回去用编辑工具（不用拷回旧副本——cargo 会以为产物是新的）；做完工作区必须干净。`做了，补了用例` 的每一行都要有这样的记录。

### 4.7 手册的原句（M6-D7）

每一句对着手册里说这件事的原句读。出处按次序：兼容性清单那一行的「Surge 行为」一格；`docs/reports/2026-10-16-phase3-manual-recheck.md`（阶段 3 相关的 87 页逐行对照与配置键一览）；`docs/reports/2026-10-28-manual-6.11-recheck.md`（手册改过的四页）。三处都没有的，写“没读到”，不凭记忆；Pi 不联网（派工的规矩），由协调者取那一页的原文放进工作区再交给它。

### 4.8 拿真实的输入读

阶段 1 的两处缺口是拿真实的输入读出来的。阶段 3 照做：每个任务照手册的例子手写几份 Profile 片段（`[General]` 的 TUN 键、`[SSID Setting]`、`subnet` 组与 `SUBNET`、`PROCESS-NAME` 的三种写法、`[IP Rewrite]`、`block-quic`、`hijack-dns`、`always-real-ip` 等），用不起守护进程的子命令过一遍——`rurge check -c <文件> --json`、`rurge rule match -c <文件> <名字> --explain`——看有没有被悄悄跳过或读成别的意思的行。不手工运行 `rurge run` 与 `rurge dns lookup`（派工的规矩）；片段与输出放工作区，报告里摘要。

`rurge rule match` 缺省会读本机真实的网络（隐藏的 `--network-backend` 选项）、会解析目标、会下载外部资源，所以每次都带 `--network-backend file:<工作区里的文件>`（一个不存在的文件，或照测试的网络后端写的假网络）、`--no-network`、`--data-dir <工作区里的目录>`，以及 `--resolve <地址>` 或 `--no-dns`；片段里只用保留的名字与回环、文档地址，`dns-server` 写回环（M6-D20）。

## 6. 第 14 节八条验收标准

每一条写四种证据，没有的照实写“没有”，不写成通过：

| 证据 | 写什么 |
| ---- | ------ |
| L1 | 内存设备与假实现上的用例：文件与名字（脚本核对存在），全量门禁那次运行的数字（一台机器上的一次运行，不是 CI） |
| L2 | 特权用例的名字；没有运行过（总设计 Q4） |
| L3 | 手工清单里证明这一条的项，按平台；一项也没有做过 |
| CI | 最近一次运行（编号、提交）是否覆盖了这条的 L1 用例；M5 之后加的用例 CI 有没有见过 |

各条的读法：

1. 浏览器、命令行工具与不支持代理的应用的流量出现在请求记录里并按规则分流——L1 是经内存设备与引擎的 TCP、UDP、DNS 端到端用例；L3 是三个平台各自的“开增强模式、用不认系统代理的工具发请求、读 `recent`”的项。
2. `ping` 正常——L1 是假的 ICMP 发送与回显的用例；L3 是三个平台的 `ping` 项。
3. fake-IP 映射与真实连接一致——L1 是应答器给的地址、连接到来时反查的名字、规则看到的目标、回包来源的用例。
4. 网络切换后 30 秒内恢复——L1 是假探测器下去抖与下游时序的用例；L3 是真的换网络、睡眠唤醒的项。
5. `PROCESS-NAME` 在三个平台命中——L1 与 CI：三个平台的 CI 上查测试进程自己的用例（运行 40611702392 通过）；L3 的三个平台各一项。
6. 性能基准达到 NFR-01 目标的 70% 以上——M5 重跑的 B1、B2、b3（内存设备，一台机器，不是 CI）：B1 八行都过线；B2 门槛读数在线内、保守读数超线（归所有者，M5 延后第 4 行）；b3 的 p99 在线内、最大值是线的 22.7 倍。真实设备上的数没有量（Q7）。
7. 需求逐句对照过代码，三个数照实写——就是本文档的第一部分。
8. 三平台 CI 绿——任务 8 读回的那次运行；没有推送之前写“M5、M6 的提交 CI 没有见过”。

每一条最后一句写“还缺什么”：照现在的证据，第 1 ～ 6 条都缺真机上的验收，第 8 条缺 M5、M6 的那次 CI。**第 14 节没有一条能因为 L1 全绿就写成“通过”。**
