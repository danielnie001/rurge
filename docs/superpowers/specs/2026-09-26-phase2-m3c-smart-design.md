- 日期：2026-09-26
- 状态：项目所有者逐节确认（2026-09-26），待审阅全文
- 依据：`docs/superpowers/specs/2026-09-23-phase2-m3-groups-subscriptions-design.md`（下称"M3 设计"）第 7 节、第 2 节的 M3-D11 / D13、第 14 节的 V10；M3b 计划 `docs/superpowers/plans/2026-09-25-phase2-m3b-testing-auto-groups-plan.md`「延后事项」#6、#14；Surge 手册 `policy-groups/smart.html`、`policy-groups/overview.html`、`policy-groups/parameters.html`（2026-09-26 读取）
- 与 M3 设计的关系：本文细化 M3 设计第 7 节，并按 M3b 落地后的代码结构（`TestBook`、`AutoGroups`、注册表的 `choose` / `standing`、引擎的 `resolve_ready`）给出接口与语义。两者不一致处以本文为准，差异逐条列在第 14 节。

## 1. 目标与范围

### 1.1 目标

让 `smart` 组按真实连接的质量自动选成员：以首字节耗时为主的时间加权分数、失败罚分与失败标记、`policy-priority` 因子、按站点记忆，选中的成员拨号失败时按重试列表换成员；测速固定 5 分钟一轮、成员多时抽样。完成后 FR-GRP-01 的五种自动选法全部可用，`W0008` 只剩 `subnet`。

### 1.2 范围内

| 需求 | 内容 |
| ---- | ---- |
| FR-GRP-01 | `smart` 的选择算法（打分、优选集、重试列表、站点记忆） |
| FR-GRP-03 | `policy-priority` 生效（M3a 已解析与校验） |
| FR-GRP-06 | `smart` 组的临时覆盖（沿用 M3b 的 `POST /v1/policy_groups/select`） |
| 总设计第 10 节 | `test_results` / `policy_groups/test` / `policy_groups/select` 覆盖 `smart`；请求记录两列耗时 |
| M3b 延后事项 #6 | `smart` 不再 `W0008`、不再取第一个成员、进 `test_results`、`select` 接受；请求记录两列耗时 |
| M3b 延后事项 #14 | 每次拨号为每个成员重建 `TestCase` 的开销（在 `smart` 打分走同一路径之前处理） |

### 1.3 范围外

- UDP 信号（UDP 响应延迟、UDP 的静默失败）：M5（M3-D11）。
- 在已建立的连接上换成员（缓存客户端首批字节重放到另一成员）：不做（M3-D11，第 2 节 M3c-D10）。
- TCP 重传率：拿不到，用失败罚分近似（M3-D11）。
- "网络已变化"触发的重测与清零：阶段 3（与 M3b 相同）。
- 选择变更通知与 `no-alert`：阶段 6。

## 2. 已确认的决定

沿用 M3 设计的 M3-D11（失败率近似重传率；只在拨号阶段换成员，"3 秒无响应"只计入打分；UDP 信号等 M5）与 M3-D13（常数由 rurge 自定，集中在一处，见第 9 节）。本次新增：

| 编号 | 事项 | 决定 |
| ---- | ---- | ---- |
| M3c-D1 | 实现方式 | 沿用 M3b 的分工：`rurge-policy` 里的 `SmartBook` 打分与选择，注册表给出选中成员与重试列表，引擎的拨号循环换成员并回报质量。不把 `smart` 组做成出站（那样会话链看不到用的是哪个成员，明文 HTTP 的绝对 URI 转发也要另做一套）（项目所有者，2026-09-26） |
| M3c-D2 | 分数与站点记忆按什么记 | 按策略记：同一节点在几个 `smart` 组里共享分数与站点记忆；`policy-priority` 在各组选择时再乘 |
| M3c-D3 | 首字节与"3 秒无响应"的起点 | 都从出站连接就绪起算（手册："the time from connecting until the first response byte arrives"） |
| M3c-D4 | 谁回报质量 | 只有经 `smart` 组选出成员的会话（含 DNS 会话）；测速结果另由 `TestBook` 推送 |
| M3c-D5 | 在哪里换成员重试 | 只在会话拨号（`Dialer::dial`）里；DNS 会话与链的中间跳（`ChainConnector`）只用选中的成员 |
| M3c-D6 | 重试的时间 | 整条会话的连接超时仍是 10 秒；每次尝试最多用"剩余时间 ÷ 剩余尝试次数" |
| M3c-D7 | 测速结果怎样进分数 | `TestBook` 存下当前定义的结果时推送给 `SmartBook`；API 在自定义 URL 上的一次性测试不推送 |
| M3c-D8 | 视图里的"当前选择" | 最近 10 分钟用得最多的成员；最近没用过时是排序里的第一个 |
| M3c-D9 | 每次拨号的开销（M3b #14） | 每一代构建注册表时预先算好查表，拨号只查表与做算术 |
| M3c-D10 | "3 秒无响应" | 只计入打分，不在已建立的连接上换成员（重申 M3-D11） |

以上 M3c-D2 ～ D10 是按 M3c-D1 逐节细化时由项目所有者确认的（2026-09-26）。

## 4. 测量与回报

### 4.1 两列耗时（所有会话）

- `SessionHandle` 记两个时刻：**出站就绪**（`Dialer::dial` 拿到出站流时；重试时是最终成功的那次）与**首字节**（第一个上游→客户端字节被读到的时刻）。
- 首字节在读到时记，不在写给客户端之后：`pump` 下行方向的首块钩子（上行方向已有同样的钩子用于 SNI 嗅探），与明文 HTTP 转发路径的 `Counting::poll_read`。两处都是"只记一次"的原子操作，不增加每字节开销（M3 设计 V10）。
- 请求记录与 `GET /v1/requests/recent`、`GET /v1/requests/active` 增加：
  - `connectMs`：从会话开始到出站就绪（含规则匹配、DNS、`evaluate-before-use` 的等待与重试）；
  - `firstByteMs`：从出站就绪到首字节；
  - 没有对应时刻的为 `null`（被拒绝、拨号失败、还没收到数据）。

### 4.2 质量探针与 `SessionReporter`

- `rurge-policy` 定义 `SessionReporter` trait，`SmartBook` 实现它，引擎持有它。
- 拨号经 `smart` 组选出成员时，引擎在句柄上挂一个质量探针：组名、成员名、目标主机名（会话的目标，与 `SelectCtx.host` 相同）。
- 回报只是一次加锁的内存更新：不做 I/O、不写 `state.json`。

### 4.3 回报时点与分类

1. 每次拨号失败（含重试中的每一次）→ **失败**。
2. 收到首字节 → **正常**，样本是 `firstByteMs`。
3. 出站就绪 3 秒后仍没有首字节 → **无响应**：记一次失败，连接照常（M3c-D10）。
4. 上游在发出任何数据之前就关闭或出错 → **失败**。客户端先关、`kill`、空闲超时、优雅退出都不是上游的错，不回报。

第 1 点每次尝试各报一次；第 2 ～ 4 点对一条会话只报先发生的一个（"质量结论"），之后首字节再到也不改。第 3 点的计时是每条带探针的会话一个 tokio 定时器，会话结束即取消。

## 5. `SmartBook` 与打分

### 5.1 归属与生命周期

- 放在 `rurge-policy`，与 `AutoGroups` / `TestBook` 一样随引擎存续：重载与订阅更新都不清空，不持久化。
- 每个策略名一条记录，并记下该策略"是不是同一个定义"的标识（出站指纹，M2b 的复用规则；取法见 V4）：定义变了（例如订阅更新改了服务器），记录清零；策略在新一代里消失，记录删除。只改测试 URL 或超时不清零：真实连接的数据仍然有效。

### 5.2 每条记录与分数

时间一律由调用方传入（单元测试可控）。H = 半衰期 5 分钟。

- **基础分**：时间加权移动平均。记 (S, W, t₀)；时刻 t 来一个样本 x：先 S ← S·2^(−(t−t₀)/H)、W ← W·2^(−(t−t₀)/H)，再 S ← S + x、W ← W + 1、t₀ ← t。基础分 = S ÷ W（与读取的时刻无关）。
- **罚分**：独立的衰减累加器 (P, tₚ)。当前罚分 = P·2^(−(t−tₚ)/H)；每次失败：P ← 当前罚分 + 800 毫秒，tₚ ← t。
- **连续失败次数**：每次失败加一，任何一次成功清零。
- **分数** = (基础分 + 当前罚分) × 本组对该成员的 `policy-priority` 因子。因子在每一代构建注册表时按"第一个匹配的正则"预先算好，没有匹配为 1.0。

### 5.3 样本与失败的来源

- 会话回报（4.3）：正常 → 样本；失败、无响应 → 失败。
- 测速结果（M3c-D7）：`TestBook` 存下当前定义的结果时推送；通过的分数（第二次 HEAD 的耗时，或退化时的整段耗时）作为样本，失败算一次失败。`test_once`（API 给了 `url` 的一次性测试）不推送。

### 5.4 三种状态

- **健康**：有样本，且未失败。
- **失败**：连续失败 ≥ 3 次；或有样本且"基础分 + 当前罚分" ≥ 3000 毫秒（因子之前）。一次成功清掉连续失败；分数过高的，要等罚分衰减或新的快样本进来才恢复。
- **未知**：还没有样本且连续失败 < 3 次（从没测过，或只失败过一两次）。

## 6. 选择、站点记忆与重试列表

### 6.1 成员

- 每一代构建注册表时，`smart` 组只保留代理策略（订阅导入的、`M (via R)` 派生的都算）；嵌套组、内置策略、`direct` / `reject` 别名一律忽略（手册），每组在加载时记一行 INFO 列出被忽略的名字（名字不是凭据）。
- 未实现的协议照 M3b 当作恒失败的成员保留（它排在最后，只有别无选择时才会被用上，得到的是带说明的 REJECT）。
- 过滤后没有成员：空组兜底（M3-D3：默认 DIRECT，`--empty-group-reject` 时 REJECT；作中继时一律 REJECT，M3b P2）。

### 6.2 排序与选择

每次拨号，用第 5 节的状态与分数、本次会话的目标主机：

1. 排序：健康成员（分数升序）→ 未知成员（连续失败少的在前，其次按成员顺序）→ 失败成员（"基础分 + 当前罚分"升序，没有样本的排在最后、按成员顺序）。
2. 站点记忆（6.3）：
   - 某个健康成员最近在这个主机上成功过、且分数不超过最优者 2 倍 → 直接选它（几个都符合时取分数最低的）；
   - 最近在这个主机上失败过的成员 → 挪到整个排序的最末。
3. 优选集：剩下的健康成员里分数不超过最优者 1.2 倍的（至少包含最优者）；从中均匀随机选一个（随机数照 M3b 的 `load-balance`，不新增依赖）。
4. 没有健康成员：选排序里的第一个（先未知、再失败）。
5. 重试列表 = 排序去掉选中者；引擎最多用它的前 2 个（第 7 节）。

临时覆盖期间只用覆盖的成员，没有重试列表（手册："always uses the selected policy"）；`evaluate-before-use` 的等待照 M3b（第 8.1 节）。

### 6.3 站点记忆

- 键是"目标主机名 + 策略"（主机名按会话看到的原样：域名或 IP 字面量），值是最近一次结果（成功或失败）与时间；成功、失败的定义同 4.3。
- 1 小时有效；最多 4096 个主机（按最近使用淘汰），每个主机最多记 16 个策略（淘汰最旧的）。
- 按策略记（M3c-D2），几个 `smart` 组共享。

### 6.4 接入注册表

- `choose` 的 `smart` 分支调用 `SmartBook` 的排序与选择；解析结果（`Resolution`）增加两样只在经过 `smart` 组时才有的东西：重试列表（组名 + 其余成员的有序列表），与质量探针要的组名 / 成员名。一条解析链里最多一个 `smart` 组（它不接纳嵌套组）。
- 链的中间跳（`ChainConnector`）解析中继时没有目标主机：`smart` 中继照 6.2 选（没有目标主机，跳过站点记忆那一步），不重试、不挂探针（M3c-D5）。
- 视图（`current_member` 等，`live = false`）不回报、不计数、不触发测速。

### 6.5 每次拨号的开销（M3b #14）

- M3b 的 `standing` 每次拨号都为每个成员构造一个 `TestCase`（克隆 URL、出站、根证书与名字）。改为每一代构建注册表时存好"策略 → (测试 key, 是否可测)"，`standing` 直接按 (策略, key) 查 `TestBook` 的结果，不再构造 `TestCase`；真正发起测试时才构造。
- `smart` 组的"成员 + 因子"表同样在构建时算好。拨号时只剩查表与算术，`url-test` / `fallback` / `load-balance` 一并受益。

## 7. 引擎的拨号重试

- **范围**：只在会话拨号（`Dialer::dial`，含明文 HTTP 的绝对 URI 转发）里。DNS 会话只用选中的成员，照 4.3 回报；链的中间跳不重试、不回报。
- **尝试序列**：选中的成员 + 重试列表的前 2 个，最多 3 次。
- **时间**：整条会话的连接超时仍是 10 秒（`CONNECT_TIMEOUT`）；**每次尝试最多用"剩余时间 ÷ 剩余尝试次数"**——3 个候选时第一次最多约 3.3 秒，前面失败得快，后面分到的就多；只有一个候选时它独享 10 秒。不设单次上限的话，最常见的失败（节点被墙、超时）会一次吃光 10 秒，重试形同虚设（M3c-D6）。
- **哪些失败重试**：连接层面的错误——I/O、超时、代理握手、TLS、代理服务器名在本机解析失败、不可用。REJECT（例如未实现协议的成员）不重试，照现有处理（含 REJECT 的自动升级）。
- **回报**：每次失败的尝试都回报（4.3 第 1 点，也记进站点记忆）；最终成功的那次挂探针。
- **会话记录**：策略链的最后一项换成实际用上的成员；换过成员时备注写固定文本，只含组名与成员名（不带地址与凭据），如 ``smart group `G`: `A` failed to connect, used `B` ``；全部失败时会话以最后一次的错误失败，备注列出试过的成员，如 ``smart group `G`: tried `A`, `B`, `C` ``。
- `evaluate-before-use` 的等待（M3b `resolve_ready`）在重试循环之前；`use-local-host-item-for-proxy` 的地址替换对每个候选照常适用（它们都是代理）。

## 8. 测速节奏、视图与 API

### 8.1 测速

- 沿用 M3b"拨号触发一轮"的机制；`smart` 组的过期固定 5 分钟（`interval` 在加载时已给 `W0028`）。
- 触发条件：上一轮结束超过 5 分钟，或有成员处于"未知"状态（5.4）。`smart` 的成员都不是组，用 `SmartBook` 的状态代替 M3b 的"没有测试结果"：有真实流量样本的成员不算未测。
- **抽样**：成员超过 12 个时，常规一轮只测 12 个——最近 10 分钟用得最多的 6 个，加最久没测的 6 个（没测过的优先）；重叠时用"最久没测"补足。首次启动时这会连续几轮把全部成员测一遍（每轮 12 个），之后回到 5 分钟一轮。
- 手动触发（`POST /v1/policy_groups/test`）测全部成员；`POST /v1/policies/test` 不变。
- `evaluate-before-use` 照 M3b：等首轮测完（等待上限按这一轮实际要测的成员算）；测完仍没有健康成员，本次会话以 `policy group evaluation failed` 失败。
- 测速结果按 5.3 推送给 `SmartBook`。

### 8.2 使用计数

- 每个 `smart` 组、每个成员，每成功用上一次（最终连上的那个成员）记一次；按分钟分桶，只留最近 10 分钟。用于抽样（8.1）与"当前选择"（8.3）。

### 8.3 视图与 API

- `GET /v1/policy_groups/select` 与 `GET /v1/policy_groups` 里 `smart` 组的"当前选择"：最近 10 分钟用得最多的成员（手册："the most-used one in the recent period"）；最近没用过时，是排序里的第一个（不看站点记忆、不随机）。读取无副作用、不触发测速。
- `GET /v1/policy_groups/test_results`：列出 `smart` 组，内容与其它自动组相同（成员 → 最近测速结果）。不新增"分数"接口（Surge 没有，YAGNI）。
- `POST /v1/policy_groups/select`：对 `smart` 组即临时覆盖，空字符串清除（同 M3b）。
- `POST /v1/policy_groups/test`：对 `smart` 组测全部成员，返回测完后健康的成员。
- `/v1/requests/*`：`connectMs` / `firstByteMs`（4.1）。

### 8.4 能力表

翻转 `smart`：此后 `W0008` 只会因 `subnet` 出现（阶段 3）。翻转任务核对本文承诺的行为都已存在（M2 设计第 8 节的教训）。

## 9. 常数（M3-D13）

集中在 `rurge_policy::smart` 的一处常量里，便于以后调整。

| 常数 | 取值 |
| ---- | ---- |
| 移动平均与罚分的半衰期 | 5 分钟 |
| 失败 / 无响应罚分 | 800 毫秒 |
| 标为失败 | "基础分 + 当前罚分" ≥ 3000 毫秒，或连续 3 次失败 |
| 优选集 | 最优者的 1.2 倍以内 |
| 站点记忆 | 1 小时；4096 个主机；每主机 16 个策略；直接选用的上限为最优者的 2 倍 |
| 无响应判定 | 出站就绪后 3 秒 |
| 拨号重试 | 最多再试 2 个成员；每次最多用"剩余时间 ÷ 剩余尝试次数"，总计仍为 10 秒 |
| 测速 | 固定 5 分钟；成员超过 12 个时常规一轮测 12 个（6 常用 + 6 最久未测） |
| 使用计数 / 当前选择 | 最近 10 分钟，按分钟分桶 |

## 10. 错误处理、可观测性与安全

| 层 | 策略 |
| -- | ---- |
| 凭据 | 回报与站点记忆里只有组名、成员名、目标主机名，只在内存里；备注文本只含组名与成员名；测试 URL 的既有规则（M3b）不变 |
| 日志 | 成员在"健康 ⇄ 失败"之间切换时记一行 INFO（组名、成员名）；被忽略的成员在加载时 INFO 一次（6.1）；不记 URL、不记凭据 |
| 上界 | `SmartBook` 记录数 ≤ 策略数；站点记忆 ≤ 4096 个主机 × 16 个策略；使用计数只留 10 分钟；测试并发仍 ≤ 8 |
| 锁 | `std::sync::Mutex`，不跨 `.await`，锁内不做 I/O；回报与选择各是一次短的加锁更新 / 读取 |
| 等待 | 重试总时长 ≤ 10 秒，单次按 M3c-D6；3 秒定时随会话结束取消；`evaluate-before-use` 照 M3b 有界 |
| 会话记录 | 重试的备注是固定文本（第 7 节）；`evaluate-before-use` 失败沿用 M3b 的文本 |

## 11. 测试策略

只用前两层（M3-D12）。测试配置里的 `proxy-test-url` / `internet-test-url` 一律指向回环（`smart` 组会真的跑测速）；只用回环 + 端口 0 + 有界等待；不修改本机系统代理与网络设置。

**第 1 层（`rurge-policy` 单元，时间由调用方注入）**：
- 移动平均：半衰期、与读取时刻无关；罚分的衰减与叠加；失败标记（连续 3 次、分数 ≥ 3000）与恢复；`policy-priority` 因子（首个匹配、没有匹配为 1.0）。
- 状态与排序：健康 / 未知 / 失败的顺序与各自内部的顺序；1.2 倍优选集（至少含最优者）；没有健康成员时的选择。
- 站点记忆：2 倍以内直接选用、失败挪末尾、1 小时过期、4096 个主机淘汰、每主机 16 个策略。
- 重试列表的顺序；抽样（6 + 6，重叠补足，没测过的优先）；使用计数的分桶与 10 分钟窗口；定义变化清零、只改测试 URL 不清零；测速结果推送（`test_once` 不推送）。
- 注册表：`smart` 成员过滤（嵌套组、内置、别名被忽略）、过滤后为空的兜底、覆盖期间没有重试列表、预先算好的查表与之前的 `standing` 结果一致。

**第 2 层（回环）**：
- 引擎端到端：三个假上游——拒绝连接的、接受 TCP 却不回代理握手的（"黑洞"，只用回环）、正常的——`smart` 在单次时限内换到正常成员；会话链、备注、`connectMs` / `firstByteMs` 正确；无响应计入失败（定时类用例先完成真实 socket 往返，再暂停时钟，M2b 的教训）。
- 临时覆盖与清除、`evaluate-before-use`、`test_results` / `policy_groups/test` / `select` 对 `smart` 组的行为。
- `rurge-api`：请求 JSON 的两个新字段。
- CLI：`rurge check` 对 `smart` 组不再报 `W0008`，`W0008` 只剩 `subnet`。

## 16. 任务草图

一份计划，约 8 个任务：

1. 请求记录两列：`SessionHandle` 的两个时刻、首字节的两个记点、`RequestRecord` 与 API JSON（V1、V9）。
2. 每一代预先算好的测试查表（M3b #14）：`standing` 不再构造 `TestCase`，结果与之前一致（6.5）。
3. `SmartBook` 打分：记录、移动平均、罚分、状态、定义变化清零、测速结果推送（第 5 节，V4、V5）。
4. 选择：排序、站点记忆、优选集、重试列表、使用计数；注册表接入（成员过滤、因子表、`choose` 的 `smart` 分支、`Resolution` 的新字段、视图）（第 6 节，V8）。
5. 引擎：质量探针（首字节、3 秒、结束分类）与拨号重试循环（第 4、7 节，V2、V3、V7、V11）。
6. 测速节奏：`smart` 的触发条件、抽样、手动轮测全部；`automatic()` 包含 `smart`（`select` 覆盖、`test_results`、`policy_groups/test`）（第 8 节，V6）。
7. 能力表翻转与端到端用例（第 11 节，V10）。
8. 文档：兼容性清单、`docs/api` 两份、README 两份、`CLAUDE.md`、手工验收、本文件与 M3 设计的实施期订正。

## 18. 实施期的订正

按计划实施时由各任务的评审发现、与上文不同的地方；计划「执行期修正记录」里有对应的行。

| 本文原文 | 实际 | 依据 |
| -------- | ---- | ---- |
| 6.1 未实现的协议当作恒失败的成员保留，排在最后，只有别无选择时才会被用上 | 不进排序：既不会被选中，也不进重试列表；组里一个能用的成员都没有时，才取组的第一个成员，得到带说明的 REJECT（Task 4） | 排在最后时，所有能用的成员都在某个站点失败过一次就会轮到它：该站点的会话在站点记忆过期前（至多一小时）都被拒绝，且不重试 |
| 8.1 抽样：成员超过 12 个时，常规一轮只测 12 个 | 按测得了的成员数算，也只在它们里面抽：协议尚未实现、测试 URL 解析不了的成员不占名额（Task 6） | 它们永远"没测过"，会一直占掉"最久没测"的名额，其余成员测不到 |

| §10 成员在"健康 ⇄ 失败"之间切换时记 INFO；§17 的 P4：只记会话回报引起的切换 | 有过会话回报的策略（经 `smart` 组用过的成员），测速推送引起的切换也记；只被测速过的策略照旧不记（终审） | 节点掉线后第一次失败就不再被选中，此后的切换都由测速推动，照 P4 这两行几乎不会出现 |
| 4.3 3 秒无响应的定时"会话结束即取消" | 定时任务不取消：到点时会话已结束、客户端一侧已经结束或首字节已到，就什么也不做（其间多持有出站至多 3 秒）（终审） | 效果相同且有界；"客户端一侧已经结束"是终审补上的，此前客户端先走、上游一直不回话时仍会记一次失败 |
