# 阶段 3 / M6「收尾与验收」实施计划

> **执行方式**：交给 Pi，由协调的会话逐个任务派工、逐个任务评审（设计第 2、9 节，M6-D13、D14；做法同 M5）。
>
> - 协调的会话每个任务开一个 Pi 会话，交给它这个任务的全文（派工文件）。Pi 做完把报告写进派工文件指定的路径，在本地提交。
> - 协调者照设计第 9 节评审：名字、抽查、改坏验证的日志、覆盖、数。有问题回到同一个 Pi 会话修正，再评审；过了才派下一个任务。
> - 任务 0 交回之后，协调者先审切法（M6-D2），再派任务 1。
> - 当场补的（设计第 4.5 节）：先写会红的用例、在没有补的代码上看到它红、再补到绿；一处一个提交（**只在本地，不推送**）。
> - 与计划的出入记进末尾的「执行期修正记录」，**不改计划的正文**。
>
> 停点：任务 8 等项目所有者推送 M5 与 M6 的提交。

**目标**：

- 阶段 3 的需求逐句对照代码，结论写进新文件 `docs/acceptance/phase3-acceptance.md`（第一部分）；

## 全局约束

**不加东西**

- 不加外部包，不加工作区依赖边。`Cargo.lock` 的包数在 `7c5753e` 是 519 个，每个任务做完照旧。
- `unsafe_code`：不加放开的函数。`crates/rurge-platform/tests/unsafe_functions.rs` 的 `LISTED` 仍是 23 项。
- 不加功能、诊断码、命令行选项、API 端点、日志行。当场补的只能是设计第 4.5 节的尺度；要加这些的，登记。
- 不改已经登记的行为（M6-D5）：兼容性清单、`docs/api/phase3.md`、手工清单里写着的行为，要改它就是改登记——登记，交给项目所有者。
- 只补本机能编译、能运行的代码：要改的地方只在 Linux 或 macOS 上编译的（`cfg(target_os = "linux")`、`cfg(target_os = "macos")`、`cfg(unix)`），不改，登记。

**缺省的 `cargo test` 不碰系统**

- 不建网卡，不改系统的任何设置；不执行 `netsh`、`route`、`ipconfig`、`ifconfig`、`ip`、`resolvectl`、`networksetup`、`netstat`、`arp`、`sysctl`，不读真实的网络环境。
- 补的用例只用回环、内存设备（`rurge-tun` 的 `MemoryDevice`、`GatedDevice`，引擎用例的 `Rig`）、各模块的假实现与用例自己的临时目录。

**测试与改坏验证**

- `CLAUDE.md`「测试约定」整节适用。写 `rurge-tun` 与经引擎的 TUN、DNS 用例之前，读 `docs/testing.md`「测试约定（全文）」里对应的一节。
- 改坏验证照设计第 4.6 节：
  - 动手之前，在日志里写下这一改会让哪些会话、查找、下载与文件去哪里；可能离开回环或写到用例的临时目录之外的，不做。
  - 日志是工作区的 `task-N-mut-<序号>.log`：改了哪个文件的哪一行（改前、改后）、跑的命令、红的输出的摘录、改回之后 `git status --short` 为空。
  - 改回去用编辑工具，不用拷回旧的副本（它保留旧的修改时间，cargo 会接着跑旧的二进制）。
- 新写的带等待的用例，提交前单独循环跑二十次以上。

**拿真实的输入读**（设计第 4.8 节；P11）

- 只用两条不起守护进程的命令，二进制是 `target/debug/rurge.exe`（门禁会编好它；没有时 `cargo build --workspace --bins`）：
  - `rurge check -c <文件> --json --data-dir <工作区里的目录>`；
  - `rurge rule match`：每次都带 `--no-network`、`--data-dir <工作区里的目录>`、`--network-backend file:<工作区里的文件>`，并带 `--resolve <地址>` 或 `--no-dns`。`--network-backend` 指一个不存在的文件（网络"什么都不知道"），或照 `rurge_platform::netenv::Snapshot` 的形状写的假网络（`docs/testing.md`「只供测试的后端」一段）。
- Profile 片段里的名字只用保留的名字（`.test`、`.example`、`.invalid`），地址只用回环与文档地址；`dns-server` 写 `127.0.0.1`，不写 `system`、`syslib`。
- 不写远程的 `RULE-SET` / `DOMAIN-SET` / `#!include`、托管配置。
- 片段与输出放工作区的 `inputs/task-N/`，报告里摘要。

**门禁与这台开发机**（说"通过"之前必跑）

- 门禁：`cargo fmt --all --check && cargo clippy --all-targets -- -D warnings && cargo test -j 8 --workspace --no-fail-fast`。
- 本机 msvc 工具链没有 rustfmt。跑 `cargo fmt` 之前让环境变量 `RUSTFMT` 指向 gnu 工具链里同版本的 rustfmt：用户目录下的 `.rustup\toolchains\stable-x86_64-pc-windows-gnu\bin\rustfmt.exe`。不要为此安装或升级工具链。
- 聚焦地跑用例也经整个工作区：`cargo test -j 8 --workspace --lib -- <过滤词>`；可执行文件的单元用例 `--bins`；集成测试 `--test <名字>`。**不用 `-p`**（它另编一份依赖，写满过 D: 盘）。
- 跑全量之前 `df -h /d`：剩余不足约 15 GiB 就停下报告。
- 测试二进制以 `STATUS_HEAP_CORRUPTION` 或 `STATUS_ACCESS_VIOLATION` 退出：单独重跑那一个二进制，报告里写明。rustc 在增量编译里报内部编译器错误：删掉出错的那个目标在 `target/debug/incremental/` 下的目录再编。
- 基线（P13）：86 个结果行、4720 通过、0 失败、13 忽略。补了用例的任务，通过数应当是基线加上新的用例。
- 只改了文档的任务不跑测试：报告里写一行 `git diff --stat <任务开始的提交> HEAD`，只有 `docs/`、`CLAUDE.md`、`README.md`、`README_en.md` 下的文件。
- 结果照实记：本机的全量运行是"一台机器上的一次运行，不是 CI"。

**仓库的规矩**（`CLAUDE.md`「必须遵守的规矩」整节适用；与本计划直接相关的）

- 照实记录：没有证据的写"没有"，不写成通过；L2 写"没有运行过"；没有在某个平台上编译、运行过的代码，照实说。
- 称齐备：照设计第 11 节，只在任务 7 写。
- 凭据：Profile 片段与文档的例子里不写真的凭据，口令写 `password` 一类。
- 去向写着"项目所有者"的事（设计第 13 节，与读的时候查出来的）不定：登记，列出来。
- 记录：计划两张表里已写下的行不改写；阶段 1、2 的验收文档只在开头加一句（M6-D15），正文不改；`docs/api/phase3.md` 各里程碑的历史段落不改。
- 文档用写文件 / 改文件的工具改。**永远不要用把一个文件的内容经管道写回同一个文件的命令**（`Get-Content x | Out-File x -Append` 一类；2026-10-27 这样写满过 D: 盘）。

**写法**

- 验收文档照 `phase1-acceptance.md` 的写法：
  - 一行一句，表的一格不换行；
  - 代码写 `路径::函数`；
  - 用例写"`路径`：`名字`（断言了什么）"。
- 文档里写里程碑带上阶段（"阶段 3 / M4b"），不写光秃秃的"M4b"。
- 不写本机路径；验收文档里不写流程用语（"派工""账本""Pi 会话"），读的人写"一个助手"，抽查的人写"协调者"。
- 补的代码：注释、日志与错误文本用英文，照所在文件的写法。注释里提到修正记录，写 `the phase 3 / M6 plan's execution record row N`。
- 提交说明照 `git log` 的样子：`docs: …`、`test(…): …`、`fix(…): …`，标题用中文；Pi 的提交不带署名行。只在本地提交：不 `push`、不 `pull`、不 `fetch` 远端、不 `amend`、不改写历史。

**不做的事**

- 只运行本仓库构建出来的二进制与 Pi 自己。不下载、不安装任何东西（含 `rustup target add`）。
- 不手动跑 `rurge run`、`rurge dns lookup`；`rurge service` 只用 `--dry-run`。手工清单里的项一项也不执行（那是项目所有者在真机上做的）。
- 参考实现：GPL 的（sing-box、mihomo、Xray-core）只取事实，代码不抄。

**计划没有写到、要做决定的地方**

- 能按设计与总设计的原则定的：自己定，记进修正记录，写"执行者的裁定"。
- 去向写着"项目所有者"的，或会改变 M6-D1 ～ D16 的：停下来列出，交给协调者。
- 现有用例变红：停下来，记进修正记录，不顺手改期望值。

### 骨架的样子

章节照设计第 5 节：

1. `## 怎么读`：先放六列（设计第 4.2 节）与八种结论（设计第 4.4 节）的定义，照抄设计的字；其余由任务 7 写。
2. `## 结论`：只写"（任务 7 写）"。
3. `## 第一部分：需求逐句对照代码`，下面依次是：
   - 入站（FR-IN）、出站（FR-OUT）、策略组（FR-GRP）、规则（FR-RULE）、DNS（FR-DNS）、配置与观测（FR-CFG、FR-OBS）；
   - 第 7 节范围里没有编号的：「预匹配在 DNS 与 SYN 层」「`[IP Rewrite]`」两张小表；
   - 阶段 1 与阶段 2 推过来的；
   - 非功能需求；
   - 数字（任务 7 写）；
   - 没有做完的、需求文字的问题、有意不同的、本机没有能红的用例的——四张表先只有表头（P18）。
4. `## 第二部分：总设计第 14 节八条验收标准`、`## 靠手工验收的`、`## 靠 CI 的`、`## 留给项目所有者的`：只写"（任务 7 写）"。

对照的表都是六列：`| 需求 | 这一句 | 结论 | 代码 | 用例 | 真机上 |`。

- 「需求」一格：需求编号；推过来的那张表写编号与出处（例如 `FR-CFG-17（阶段 1 对照第 154 行）`）；第 7 节的两张小表写 `第 7 节`；非功能需求写 `NFR-01` 一类。下面切法的「备注」里写着出处的行（`阶段 1 对照第 N 行`、`阶段 2 验收第 N 行`），出处也写进「需求」一格，例如 `FR-RULE-01（阶段 1 对照第 196 行）`（P4）。
- 「阶段 1 与阶段 2 推过来的」一节，表之前写一句：这张表只列没有并进别的表的句子；并进去的，出处写在那一行的「需求」一格里（阶段 1 对照第 160、196 ～ 198、205、263 ～ 265、323 行，阶段 2 验收第 26、360、520 行）。
- 「这一句」一格：用需求自己的话引，长的用 `…` 缩短；第 7 节的两张小表与 FR-CFG-06 的几行引兼容性清单那一行的话，括号里写清单的节。

- 别的三格空着。指向另一行的行（P4），「代码」一格先写"同「<表>」的「<那一句>」一行"。

## 任务 1 ～ 5 共同的做法

每个任务读骨架里结论写着 `待读（任务 N）` 的那些行。

**每一行**

1. **手册的原句**（设计第 4.7 节）：照兼容性清单那一行 → 阶段 3 的手册报告 → 6.11 复查报告的次序找。三处都没有的，写"没读到"，接着读别的行；报告里列出这些行，协调者取那一页的原文放进工作区，在修正轮里交给你。不凭记忆，不联网。
2. **代码**：真正作用于这件事的地方，写 `路径::函数`。只有解析器接受它而没有东西用它的，不算"做了"。
3. **用例**：读它的断言。写"`路径`：`名字`（断言了什么）"。
   - 用例只在某个平台上编译的，写明平台。
   - 写明 CI 见没见过：CI 运行 40611702392 跑的是 `3a76b80`；`git grep -n "fn <名字>" 3a76b80 -- <路径>` 有结果的写"CI 运行 40611702392 通过"，没有的写"CI 没有见过"（P14）。
4. **结论**：设计第 4.4 节的八种之一，别的写法都不用。`不属于阶段 3` 与 `需求文字有问题` 的后面括号里用一句话说为什么。
   - 第八种 `做了，本机没有能红的用例` 有两种情形：只在 Linux / macOS 上编译的；本机编译、但只在有特权、真设备或签名的 DLL 时才运行的（直接调操作系统的 FFI、真的执行系统命令的那一层）。代码一格写明是哪一种（它的 `cfg`，或"要特权 / 真设备 / DLL"）。
   - L1 的用例把逻辑一直钉到系统的边界（假执行器收到的逐字命令、路由集、恢复的计划），改坏那段逻辑会有用例红的，记 `做了`；系统真的照做没有，是"真机上"一格的事（设计第 4.4 节，阶段 1 FR-IN-04 的先例）。
5. **真机上**：设计第 4.3 节。
   - 写手工清单的编号（`docs/acceptance/phase3-manual.md`），按平台写；
   - L2 的用例写名字与"（没有运行过）"：`tests/privileged/tests/linux_netns.rs` 的三条，`crates/rurge-platform/src/tun/windows/wintun.rs` 的 `a_real_wintun_dll_passes`；
   - L1 已经证明了全部的写 `—`；
   - 要真机、但真机上也没有一项手工操作看得出的，写 `看不出（<为什么>）`（例如 `udp-priority`）；
   - 要真机而清单里没有的写 `缺`（任务 6b 补）。
6. **指向别的行的行**（P4）：结论与「真机上」照被指的那一行；「代码」一格写"同「<表>」的「<那一句>」一行"；「用例」一格写"同上"。被指的行在别的任务里的，等那个任务读完；你的任务里先写 `待读（任务 M）`，由任务 M 一起填。

**`做了` 的每一行**：读断言读不出它会因这一句不成立而红的，做一次改坏验证（全局约束）。`做了，补了用例` 的每一行都要有改坏验证的日志。

**当场补**（设计第 4.5 节）：

- 一处代码、一条用例补得上的，当场补：先写用例；在没补的代码上跑，看到红；再补到绿。一处一个提交。
- 那一行记 `补上了`，用例一格后面括号里写提交的短哈希。
- 要先有设计、要加依赖、要动只在 Linux / macOS 上编译的代码、要改登记的：不补，记 `没有做完（已登记）`。
- `rurge-platform` 与 `rurge-tun` 里本机编译、缺省用例跑得到的代码可以照同样的尺度补；加或改 `unsafe` 的函数、FFI 的调用、新的平台后端、在真机上执行的系统命令的内容，不补，登记（M6-D23）。

**登记**（P18）：

- `没有做完（已登记）`、`需求文字有问题`、`有意不同（已登记）`、`做了，本机没有能红的用例` 的每一行，同时在第一部分末尾对应的那张表里加一行。
